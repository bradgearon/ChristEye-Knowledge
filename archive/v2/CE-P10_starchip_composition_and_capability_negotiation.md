# 1 Purpose and boundary

Build larger Stars from smaller chips while preserving interfaces, independent test evidence and clear responsibility for errors.

# 2 Inputs

- Composition manifest with component IDs, accepted version ranges

- Input/output compatibility and evidence profiles

- User-selected goals and fallback modes

# 3 Outputs / Winds

- Resolved composite StarChip manifest and dependency graph

- Integration test plan and attribution report

- Warnings on incompatible claims or scarce resources

# 4 Required behavior

- Require declared conversions between incompatible Wind types.

- Prevent accidental cyclic dependencies or implicit hidden shared state.

- Select arbitration policies by measured benefit, not fictional persona ratings.

- Allow combined experience designers to invoke music, narrative and art asynchronously.

# 5 Processing and activation

> **1.** Resolve versioned capabilities and dependencies.
>
> **2.** Validate a cycle-free execution graph and data permissions.
>
> **3.** Run contract tests and end-to-end simulation.
>
> **4.** Measure composite output with component ablations.

# 6 Test and release gate

- Composite benchmark is not merely the average of component scores.

- Removing a child module yields a defined degraded behavior.

- Per-component quality and responsibility remain auditable.

# 7 Failure and protection

- Compositional hallucinations despite individually good modules.

- False gains caused by increased digital compute budget.

# 8 Open research and engineering questions

- Should compositional policies be hand-authored for production games?

# 9 Data contract and evidence trace

All calls use versioned request/response schemas. A WindEnvelope records source, recipient, trace_id, data type, delivered time, validity, provenance and uncertainty. Actual hardware commands, if any, require a separate approved permit. Performance claims cite evaluator runs with sealed test sets.
