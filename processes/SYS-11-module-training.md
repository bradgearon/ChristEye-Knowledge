# SYS-11 · StarChip training, specialist packages, filesystem and digital development

**Purpose:** turn the modular Anaiero specification into a buildable software process while keeping biological learning as an independent scientific claim.

## Software subsystem implementation

Each StarChip declares version, purpose, source/recipient ACL, accepted events, state serialization, curricula, dependency DAG, protected capabilities, evaluation suite, resource budget and digital CrystalPack compatibility.

**Core package families:** Memory/Roots, Lotus, WindBus, Scientist, Cell Foundry, SustiBus/ChemiBus, Observer, Metroidvania/GPU-like world production, music/genre composition, scientific theorizing, discipline trainer, book and small software updater. These are digital software roles. A domain/subject does **not** need a separate biological organoid unless a later study specifically justifies one.

## Teaching curriculum

- **Bread:** prerequisites, grounded source chunks, worked examples, minimal independent tests and basic retrieval cases.
- **Meat:** advanced transfer problems, multistage projects, ambiguity, tool integration and cross-domain constraints.
- **Honey:** scored feedback delivered *only* within a declared teaching trial; the sealed evaluator remains separate from teacher inputs.
- **Milk:** qualified physical support; never included in the same software reward channel.
- **Water:** digital source access or physical exchange according to explicit scope, never a generic mix of both.

Training sequence: freeze intended skill and existing baseline → partition source/training/validation by episode and time → train or replay *digital* examples → test unseen cases and delayed use → noninferiority on prior skills → produce signed capability certificate → allow installation by controlled dependency/permission route. A Crystal comprises its manifest, source rights, content digests, training episodes, checks and model/runtime compatibility.

## Data objects

**ModuleManifest:** module_id, version, inputs, outputs, interfaces, capacity estimate, dependencies, permitted actions, model state/compatibility, health/version gates, evidence status.  
**TrainingPlan:** curriculum_ids, prerequisite graph, intended proficiency, holdout hash, evaluation IDs, planned interventions, cost limit and protected-skill contract.  
**MemoryArchive:** immutable object hash, legal/source permission, index generation and recall route.  
**CrystalManifest:** skill claim, input/output reader compatibility, immutable assets, installed target, replay mode, held-out probes and lineage of source edits.

## Digital examples and acceptance

A book Crystal installs as an indexed retrieval and self-test source; it is **not** proof that a neuron absorbed the book. A Metroidvania StarChip generates rooms and needs independent progression solvability tests, seeded replay and graph safety. A genre music pack must be evaluated on coherent outputs not only copying of examples, and source copyright permissions are recorded. Advanced theory modules must produce falsifiable experiments and distinguish real data from generated Star dialogue.

## Invariant tests

Schema/ACL validation, deterministic replay of a frozen run, per-source consent/rights, no protected data in export, independent evaluator isolation, backward-compatible reads, crash-atomic snapshot, explainable Lotus action and refusal of unqualified physical commands.

## Biological handoff

Only scoped instrument observation may cross into an experiment after separate source and hardware releases. A successful simulated Wind is not a physical neural communication channel. See [BIO-06](BIO-06-teaching.md), [BIO-07](BIO-07-joining.md), [BIO-08](BIO-08-crystals.md).
