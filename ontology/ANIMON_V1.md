# ANIMON/1 — Animon as the named system class

**Decision:** The individual developmental system envisioned by ChristEye Anaiero is called an **Animon**. It is **not primarily described as a computer**. The current implementation remains a mixed technical research program with working digital-reference components and an *unproven* living embodiment. Animon is a project-coined system-class term, **not** an accepted taxonomic designation, evidence of sentience, or trademark clearance.

**One-line definition:** *Animon* (noun): a developmentally organized individual system, specified to acquire and retain tested capabilities, coordinate specialized functional communities, depend on defined care/maintenance, and maintain a traceable history of growth and change.

This is the intended *class* of individual system; it does not assert that a fully functional biological specimen already exists.

## 1. Naming hierarchy — exact use

| Term | Role | Appropriate usage | Do not infer |
|---|---|---|---|
| **We Develop Software LLC** | Research origin and legal rights holder | Company, publication owner, future accountable operator | An independent scientific institute has automatically approved experiments |
| **ChristEye Anaiero** | Architecture, research program and WDS project | Project title, diagrams, technical publications and website | It is the name of every cell or software process |
| **Animon** | Target individual developmental system class | "An animon is designed to mature through evaluated experience and sustained care" | An actually viable, independently thinking biological unit is already produced |
| **Animon specification** | Blueprint for a future individual system | Versioned model, capability, identity/lineage and acceptance contracts | A physical specimen |
| **Animon candidate** | Proposed physical/hybrid prototype whose status is explicit | Named preparation + source and observation status + qualified research-owner record | Validated organism or conscious agent |
| **Digital Animon reference model** | Nonliving software and synthetic evaluation reference for the architecture | Executable WindBus, Lotus, Root evaluation, CrystalPack and simulated care | A living animon, organoid or biological learning result |
| **StarChip** | Domain-specialist capability module or upgrade package | Module-specific software/learning competence and interface | Every StarChip is a discrete cell/organoid |
| **Soil** | Proposed organoid *as a whole* | Living tissue preparation, neural and glial participants, matrix and history | Matrix alone, Sea, fluid culture medium or entire Animon |
| **Spinal Root tissue** | Proposed spinal-derived neural/glial subsystem | Regional/tissue structural evidence, axonal projection candidates | A proven arbitrary semantic storage region |
| **Functional Root** | Retained relationship measured under declared task conditions | Independently tested delayed learning with defined reader and controls | One neuron, one spinal anatomical segment, or a cloned memory |
| **Crest** | Cell-source lineage, production stewardship and qualified human process | Source/lot identity, cell population observations and uncertainties | A novel phenotype or a molecular ID written into every daughter |
| **Lotus / Heart / Spirit** | Named roles in Anaiero coordination, control and educational architecture | Digital roles or separately tested biological correlates with explicit labels | Emotion, cognition or consciousness merely from a role name |

**Style rule:** Use **Animon** in sentence-case when describing the class. Use *animon* in ordinary lower-case prose if the style context is generic. First use in scientific text should link to this definition; second uses should preserve the exact operational referent.

This is a **conceptual dependency graph**, not an anatomical image. Soil and spinal Root may be related components of a future preparation; a qualifying review must characterize their actual composition, relationship and I/O instead of declaring a fixed physical topology in advance.

## 3. Required distinction: identity is not cells, cloned competence or software addresses

- **animon_spec_id:** immutable versioned blueprint for what a possible individual could be.
- **animon_instance_id:** reserved identity of a particular *actually observed* candidate assembly; **null** until there is an authentic, registered preparation and owner.
- **digital_model_id:** software experiment/reference ID; it is not a physical Animon identity.
- **source_lot_id / clone_lineage_id:** qualified source and potentially shared ancestral cell lineage. Neither identifies the complete system.
- **cell_instance_id / cell_track_id:** observation/trajectory identity of one cell, with confidence and validity interval.
- **axon_projection_id:** spatial/functional candidate measurement of a neuronal process, **not** a cell and not an Animon.
- **functional_root_id:** task-specific retained relation measured under explicit evaluation; may be linked to several proposed neural sources.

A physical candidate's cell population can change over time without making its whole-system identity a count of individual cell identifiers. A genetic lineage barcode is not a guarantee that every descendant has a unique address; any cellular genomic encoding would be a separate institution-reviewed study, not a default step in creating an animon.

## 4. Proposed developmental dimensions — not a maturity score

An Animon design may develop in multiple *independently measured* dimensions:

| Dimension | Observation | Incorrect proxy |
|---|---|---|
| Identity and source history | qualified line, lot, verified permission and source transitions | a manually assigned system name |
| Structural development | actual cell counts/phenotypes, tissue region, axon morphology/route | organoid size or electrical amplitude alone |
| Learning | successful held-out acquisition under sealed evaluator and known input conditions | model confidence, constant HOLD, memorized prompt |
| Retention | delayed selective use, protected earlier competencies, fixed reader and controls | full data retrieval or a single high score |
| Care and continuity | independently sustained support and real service receipts | reward-weighted feeding |
| Coordination | traceable typed messaging, accepted decisions, hard safety veto | a decorative Lotus icon or text narration |
| Flexibility | cross-context transfer and recoverable degraded routes | uncontrolled expansion or more neurons |
| Claimed physical Crystal | defined observed carrier, reader/recipient, selective contribution and disconfirming controls | molecule presence, gel density, or symbolic "Word" |

No single scalar "Animon maturity" or "life percentage" is scientifically defensible before a qualified model and validated endpoints exist. A public UX might show **which assessments were completed**, not a misleading sentience meter.

## 5. Stage names and evidential permissions

| Status | Meaning | Permitted language |
|---|---|---|
| **DESIGN** | Architecture and hypothetical organization only | "Proposed Animon", "Animon specification" |
| **DIGITAL_REFERENCE** | Reproducible nonliving implementation/test | "Digital Animon reference model", *not* "living Animon" |
| **PHYSICAL_CANDIDATE_UNQUALIFIED** | An actual future source/preparation record is proposed or observed but not fully qualified | "Candidate Animon preparation" with owner, source and unknowns |
| **LAB_REVIEW_PENDING** | Named preparation with pending independent SOP/source/assay approvals | "Candidate under scientific review" |
| **PHYSICALLY_CHARACTERIZED** | A preparation has actually passed selected characterization gates, not learning | "Characterized preparation" with measured scope |
| **FUNCTION_TESTED** | Reproducible bounded task and valid independent evaluation | "Functionally tested candidate" with explicit results; *no* generalized mind claim |
| **SCIENTIFICALLY_REVIEWED** | Claim-specific independent analysis and signoff | State only what the reviewed evidence supports |

**Status transitions are not automatic.** A source code change cannot promote a living candidate, and a generic paper about organoids does not establish local Animon biology. All D3/D4 laboratory outcomes require authorized facility records; no current source was found in this review demonstrating that status.

## 6. Care, love, development and power — ordinary technical meanings

- **Care:** an independent sustaining-support requirement, especially for any future living preparation, with actual source-qualified care SOP and fault escalation. It is *not* selective learning feedback.
- **Love:** a WDS human-centered design and stewardship value—dignity, patient attention, non-manipulation and respectful relationships—not a measurement that living tissue has a human-like emotional state.
- **Development:** separate changes in source population, neurite morphology, synaptic participation, retained capability and software specialization; each has separate evidence and risks.
- **Power:** available electrical/computational/physiological resources with measured or specified unit and source—not an emergent unlimited energy mechanism.

## 7. Non-equivalences that must remain explicit

1. Animon **≠** conventional computer relabeled for marketing; the design centers growth, care, development and a traceable individual history.
2. Animon **≠** demonstrated organism; the project proposes a new system category without creating a biological taxon.
3. Animon **≠** a single organoid; Soil is a proposed *part* of a fuller architecture.
4. Digital reference model **≠** living individual or successful neural training.
5. Spinal Root tissue **≠** stored semantic Root by definition.
6. Digital CrystalPack **≠** a transferable biological engram, ingestible packet or cloned cellular skill.
7. Cell lineage identity **≠** learned state or uniquely encoded per-cell DNA ID.
8. A named Spirit role **≠** evidence of consciousness, intentions, free will or a validated emotional experience.

## 9. Publication, commercial name and source precedence

**ChristEye Anaiero** remains the scientific/project title, **Animon** the provisional target system class. The coined word is not a guaranteed available product mark. Before using **Animon** as an external commercial product brand or registering any class-specific trademark, WDS should request a current professional trademark clearance; this document makes no legal finding.

Existing versions remain historically correct sources and must not be silently rewritten. Future public docs should cross-reference the ANIMON/1 decision and identify superseded "living computer" as a **former project shorthand**, not the current preferred class name.
